# Fndesk 卸载残留调查与清理说明

检查日期：2026 年 10 月 18 日  
检查环境：用户自有 NAS，fnOS 1.2.0800，x86_64  
对象：此前安装并已卸载的 Fndesk 桌面管理工具。此次未记录原安装包版本和哈希，因此结论限于本机观察到的安装后状态，不代表所有版本都存在相同行为。

## 结论

本机的 Fndesk 主应用已经卸载，但它对系统网页、Docker 页面、分享页面以及系统网页恢复包的修改没有一并恢复。卸载后，系统首页仍加载其脚本；首次清理后，系统保护机制又从被修改的恢复包中重新写回这些文件。

这已经超出“留下少量配置文件”的范围，可以明确评价为：**系统改动侵入性强，卸载恢复不完整，残留会借助被修改的系统恢复源重新生效。** 从用户体验角度，将这种行为称为“流氓软件式行为”有事实基础；但“流氓软件”是带评价色彩的称呼，本次检查并未证明作者恶意，也不足以认定病毒、木马、窃密程序或作出法律定性。

## 已核实的事实

| 检查项 | 实机结果 | 影响 |
| --- | --- | --- |
| 主应用状态 | `appcenter-cli status fndesk` 与 `Fndesk` 均为 `noinstall`；未发现名称匹配的运行进程 | 主包卸载不等于系统改动已恢复 |
| 系统首页 | `/usr/trim/www/index.html` 仍包含加载 `./cqfndesk.js` 的标签 | 每次重新加载首页仍可能执行残留代码 |
| 二级脚本加载 | `cqfndesk.js` 会创建脚本标签继续加载 `./fndesk.js` | 主程序不运行，网页脚本仍可运行 |
| 桌面配置 | `/usr/trim/www/deskdata/` 留有 `data.json` 和 `fnstyle.json` | 图标与主题配置仍位于系统网页目录 |
| 登录页修改 | 存在 `FN_LOGIN_LOGO_CSS` 和 `FN_LOGIN_FOOTER` 注入块，包括访问统计脚本 | 登录界面的样式和外部脚本加载未随卸载撤销 |
| 更新文案 | 简体中文系统更新文案仍提示更新后到 Fndesk 后台“立即生效” | 系统原生提示被第三方文案替换 |
| 其他网页修改 | Docker 代码中存在 `/app/fndesk/...` 图标路径；分享页代码中存在 `fndesk_share...` 等注入标识 | 改动范围不局限于 Fndesk 自己的页面 |
| 系统恢复源 | `/usr/trim/share/.restore/www.zip` 中也包含上述残留及被修改页面 | 系统保护机制会把残留当作待恢复的内容 |

不能仅凭文件内出现 `fndesk` 字样判断被注入。例如，原生 CSS 变量中的 `fndesktop` 不等于 Fndesk 注入。本次后续判断结合了具体加载路径、脚本内容、恢复包差异和原始文件校验。

## 为什么第一次清理后又出现

22:51:34 首次备份并清理系统网页。系统日志随即记录：

```text
nginx will stop serve because some file has been modified:
/usr/trim/www/.fndesk-cleanup-mm75g9bq
```

随后 `trim_nginx.service` 自动停止并重新启动。22:51:35，注入脚本和修改过的首页重新出现。核对发现，系统使用的 `www.zip` 恢复包本身也已经包含 Fndesk 改动。

因此，回写来自飞牛原有的文件保护与恢复机制，并不是本次发现了一个独立的 Fndesk 后台“守护进程”。问题在于恢复源也被修改了。不能把这一现象直接描述为作者编写了恶意自我复活程序。

## 恢复依据和清理结果

设备保留了 `/usr/trim/share/.restore/www.bak` 原始归档，以及 `/usr/trim/share/.restore/raw/` 原始解包目录。原始归档带有加密标志，本次没有解密归档，而是将其记录的文件 CRC 与已有原始目录逐一比较。

排除目录项和 macOS `._` 元数据文件后，1,389 个文件全部匹配，无缺失、无 CRC 差异，且系统构建资源文件名对应当前版本。CRC 校验用于确认已有目录与本机原始归档的一致性，不等于对该归档进行了官方数字签名认证。

在保留备份后，以这份原始内容重建 `www.zip`，由系统保护机制恢复网页。没有禁用文件保护、停止其长期运行或修改系统服务启动策略。此前暂时改写的三条更新提示也被原始文件完整替换。

最终验证结果：

- 当前系统网页的 1,389 个文件与原始归档 CRC 全部一致。
- `cqfndesk.js`、`fndesk.js` 和 `deskdata` 已从活动网页目录移出。
- 实际 HTTP 首页返回正常，不再含 Fndesk 注入、附加登录块及不蒜子统计加载。
- 简体中文更新提示恢复为原始内容。
- 被修改的中间目录 `tow` 已隔离；原始 `raw` 和 `www.bak` 保留。
- 飞牛网页服务为 `active`，NAS 工具箱为 `running`。
- 本工具箱的桌面图标配置哈希保持不变，LibreTV 图标仍存在；未卸载其他应用。
- 浏览器重新加载后，飞牛桌面正常显示，附加访问统计不再出现。

备份和隔离内容保存在 NAS：

```text
/root/fndesk-cleanup-20261018-225134/
├── before.tar.gz       初次清理前的相关页面和配置
├── modified-www.zip   被修改的网页恢复包
├── quarantine/        移出的脚本、配置及修改后的中间目录
└── report.json        清理与验证记录
```

备份目录仅供管理员访问。恢复这些备份会重新引入原有改动，不应当作正常系统恢复包继续使用。

## 如何评价软件性质

用户合理期待“卸载桌面美化工具”后，系统不再执行其脚本，原生页面及恢复源中的相关改动也应得到恢复。保留用户主动选择保留的配置，与继续在系统页面加载代码，是两种不同情况。本机表现没有达到完整卸载的预期。

可以采用以下表述：

> 在我的 fnOS 1.2.0800 设备上，Fndesk 卸载后仍残留系统首页脚本、原生页面修改和配置，并且系统网页恢复包也被修改。仅删除网页残留会被系统保护机制重新还原。最终通过恢复原始网页及恢复包完成清理。这属于严重的卸载恢复缺陷，我认为具有“流氓软件式行为”的特征。

不宜在现有证据下宣称“确定是病毒”“偷偷窃取账号”“作者故意留后门”或“所有版本都无法卸载”。本次没有进行完整网络取证，也没有核验安装时的权限告知和用户当时选择的卸载选项。登录页加载第三方统计代码是一项可观察事实，不能据此推断已发生账号或文件泄露。

项目当前公开的卸载回调代码主要清理应用数据与元数据目录，没有展示恢复系统网页及网页恢复包的流程；这与本机表现一致。不过，该代码是检查当日的仓库内容，不能替代对原安装版本卸载脚本的核验。

参考：[Fndesk 项目仓库](https://github.com/IMGZCQ/Fndesk)、[当前公开卸载回调](https://github.com/IMGZCQ/Fndesk/blob/main/cmd/uninstall_callback)。本机检查和清理结果是上述技术结论的主要依据。
